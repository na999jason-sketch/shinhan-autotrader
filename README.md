# Shinhan Native Trader 2.2.10

신한투자증권 Indi를 사용하는 **C# .NET Framework4.8 / x86 Windows 실계좌 자동매매 프로그램**입니다. 종목 발굴, 실제 보유의 현재가·평균단가·평가손익, 현금100% 주문가능금액, 주문·체결·미체결과 날짜별 보고서를 표시합니다.

2.2.10은 **미확정 주문 대기로 전송을 중단한 동안에도 종목 분석과 보유의 손절·익절·추적손절 판정을 계속**합니다. 계좌 조회·감시에 연결하면 공개 종목 분석을 자동으로 준비하고, 주문 시작이 대사 때문에 보류돼도 남은 분석을 이어갑니다. 장중의 검증된 최신 SC로 보유 위험을 계산하며, 계좌 조회가 Busy이거나 주문 사전검증 중이어도 이 표시가 밀리지 않게 했습니다. `실계좌 잔고·손익`의 `매도판정`과 `매도 주문상태`를 분리해 손절 조건과 전송 차단 사유를 함께 표시합니다. 이 조회·분석은 주문 승인을 새로 만들지 않습니다.

**현재 실제 주문 복구는 해결되지 않았습니다.** 첨부 CSV의 기존 접수 매도는 주문수량2·누적체결2·미체결0·평균체결가83,775원으로 조회됐지만 확인구분은`1`입니다. 사용자가 제공한 Helper는`1=거부`라고 설명하므로 수량과 확인 명세가 충돌합니다.2.2.10은 이 충돌을 화면·진단·CSV에 명확히 남기며, 해당 주문을 임의로 체결완료로 바꾸거나 다시 전송하지 않습니다. 확인구분이 공란인 경우에만 독립적인 전량체결 증거를 검사하는 별도 경로가 있으며, 이번`1` 응답에는 적용하지 않습니다. 실제 설치의 `saba231q1.xtr`가 포함된 새 조회 정의와 최신 CSV로 원인을 확인해야 합니다. 상세 근거는 [확인구분 충돌과 조회·분석 유지](docs/CONFIRMATION_CONFLICT_AND_READONLY_ANALYSIS_20261113.md)에 있습니다.

2.2.9는 **거절된 매수·매도를 사용자가 행마다 다시 실행하지 않아도 현재 전략으로 자동 재검증**합니다. 실주문 운영이 시작된 동안 명시적인 미접수 거절 근거가 있는 주문을30·60·120초 간격으로 다시 검토하며, 최초 주문 이후 추가 전송은 종목·매매방향·거래일별 최대3회입니다. 대기 후에도 현재 신호가 유효해야 하고, 거절 이후 새 계좌·당일 주문 조회와 모든 시세·잔고·주문가능금액·가능수량 검사를 다시 통과해야 합니다. 전송 직전에도 재검사하며 과거 수량·가격을 그대로 보내지 않습니다.

일반 화면의 선택 재시도 버튼은 없앴습니다. `주문·체결`의 `거절 자동 재검증` 안내와 후보·매도 주문상태의 대기 사유를 확인할 수 있습니다. 접수·체결 확인 중이거나 결과 불명인 주문은 재전송하지 않습니다. 재시도 횟수와 고유 감사 기록은 재시작 후에도 유지되지만 실주문 시작 승인은 복원하지 않습니다. 과거 사용자가 HTS/MTS에서 미접수를 확인한 특정 당일 매도 기록도 별도의 제한된 자동 재평가로 연결합니다. 이는 증권사 접수·거절 증거를 새로 만드는 처리가 아니며, 상세 조건은 [거절 주문 자동 재검증](docs/AUTOMATIC_REJECTION_RECHECK.md)에 있습니다.

2.2.8은 **정상 계좌 조회 뒤에도 과거 접수 주문의 `Unknown` 상태 때문에 운영이 반복 중단되던 복구 경로**를 연결합니다. 사용자2.2.7의13:07~13:09 기록에서는 종목·잔고·현금·당일 주문 조회가 정상 수신됐지만, 재시작 후 남은 접수 매도를 해소하지 못해 주문 준비가 막히고 계좌 세션까지 해제됐습니다. 이 증상은 새 COM 수신 실패와 구분하며, 앞서 발생한 AA·AD 실시간 오류의 원인은 아직 확정하지 않습니다.

이제 `실계좌 조회·감시`의 정상 당일 주문 조회로 **이미 정상 접수된 KRX 원주문 한 건의 전량체결**을 엄격히 대사합니다. 계좌·거래일·주문번호·종목·매매구분·수량·지정가를 대조하고, 평균체결가는 지정가 범위와 기존 체결 금액에 맞으며 미체결·취소가 없어야 합니다. 계좌에 연결된 새 요청·정상 콜백·수신5초 이내 여부도 확인합니다. 일치하면 누적 체결 체크포인트를 개별 체결과 별도로 저장하며 가짜 체결번호를 만들지 않습니다. 번호 없는 불명 주문·부분체결·누락·불일치·오래된 자료는 계속 대사 대기로 남습니다.

불명 주문이나 실시간 오류가 있으면 추가 주문 승인을 해제하되, 세션 메모리의 조회 자격정보·주문 기록을 유지해 계좌 감시·대사·보고서를 계속합니다. 복구 후에도 자동으로 주문을 재개하거나 과거 주문을 다시 보내지 않으며 **`실주문 운영 시작`을 다시 눌러야 합니다.** 합성 검사와 실제 서버 복구 검증은 구분하며, 상세 근거는 [접수 주문의 전량체결 복구](docs/ORDER_TERMINAL_RECOVERY_20261113.md)에 있습니다.

2026-11-13 사용자2.2.6 실행에서 **실제 매도 주문1건의 접수가 HTS/MTS와 대응 KRX 주문번호 응답으로 확인됐습니다.** 접수 직후 실시간 수신 오류가 발생해 운영이 중단됐고, 접수된 주문은 체결 대사가 필요한 상태로 남았습니다. 이후 잔고 행수와 주문 조회값이 바뀐 사실만으로 개별 체결이나 전량 매도 완료를 확정하지 않습니다. 매수·정정·취소·전체 체결 복구의 실제 검증도 남아 있습니다.

2.2.7은 AA·AD 등 실시간 처리 실패의 이벤트 종류·필드 번호·고정 실패 분류를 남기고, 접수 응답이 확인된 주문의 화면을 `접수확인·체결대사필요`로 구분합니다. 이 표시는 양수 증권사 주문번호와 정상 접수 증거가 함께 있는 경우에만 사용합니다. 주문 행 선택과 새 응답 표시를 유지하고, 주문 채널 준비 중 중단·계좌 변경도 다시 검사합니다. 금액·수량·체결 식별자·신선도 검증이나 결과 불명의 재전송 차단은 유지합니다. 실제 실시간 오류의 원인은 아직 특정되지 않았으며, 자세한 근거와 남은 검증은 [접수 확인과 실시간 장애 기록](docs/ORDER_ACCEPTANCE_AND_RT_FAILURE_20261113.md)에 있습니다.

2.2.6은 사용자가 내보낸 실제 설치 정의를 분석해 적용했습니다. `0x0208` 직렬화와 신규39입력/8출력, 정정·취소38입력/8출력을 지원합니다. 실제 두 주문 파일을 끝까지 읽어 인식했고, 동일한 주문방식 필드의 내부 별칭·형식·폭과 Helper의 `0:SOR 1:KRX 2:NXT`를 대조해 KRX=`1`을 사용합니다. 신규37번과 정정취소35번에 이 값을 설정하고, 일반 KRX 지정가의 조건가격·SOR원주문번호는 빈 값으로 명시합니다. SOR/ORC 번호를 KRX 번호로 바꾸지 않습니다.

잔고 조회는 실제 정의에 추가된7번 `조회시세구분코드`에 `1:KRX`를 설정해8개 입력을 모두 전송하고 검증합니다. Helper가 공란의 KRX 기본값도 설명하므로, 이 누락만으로 이전 GI004 원인이 확정됐다고 표시하지 않습니다. 기존 거절 이력은 보존하며2.2.9의 자동 재검증에서도 덮어쓰지 않습니다. 실제 파일 인식·요청 생성 검증과 실제 서버의 접수·체결 검증은 구분합니다. 근거는 [현재 설치 정의 대조](docs/ACTUAL_INSTALLED_CONTRACT_20261113.md)에 있습니다.

2.2.5는 사용자2.2.4 화면의 첫 계좌조회 `RID=0 / GI004`와 주문 정의 `UnsupportedFormat`을 분리해 다룹니다. 잔고 조회 입력은2.2.3과 같으며 두 오류의 인과관계는 확인되지 않았습니다. 초기 조회에서 주문 OCX 생성·주문 정의 분석을 지연하고, 실제 주문 준비 전에 채널을 만든 뒤 계좌 근거를 새로 수집합니다. 생성 중 중단·계좌 변경은 다시 검사합니다. 읽기 전용 계좌 조회가 정확히 요청번호0·GI004로 미접수된 경우에만1초 뒤 최대1회 전체 요청을 다시 설정합니다. 주문 전송은 이 재시도의 대상이 아닙니다. 새 요청번호·실제 시작시각·정상 응답을 다시 검증하며 중단·취소·폐기·2차 실패는 계속 중단합니다. 이 변경만으로 실제 GI004가 해결됐다고 표시하지 않습니다.

설치 Helper는 최신 `qry/config/helpertrinfo.dat`를 우선하고 구형 경로는 대체 경로로 사용합니다. 두 경로의 검증된 코드가 충돌하면 거부합니다. 주문 정의를 읽지 못해도 쿼리·크기·SHA256·실패 단계·위치를 기록합니다. 사용자 설치의609 정의는3,844바이트로 기존 확보본2,981바이트와 다르지만, 이 사실만으로 주문 응답 배치나 오류 원인을 추정하지 않습니다.

`조회 정의 내보내기`를 누르면 현재 설치의 `saba609q1.xtr`, `saba101u1.xtr`, `saba102u1.xtr`, `saba231q1.xtr`와 Helper의 정적 정의를 XML 파일 하나에 저장하고 폴더에서 선택합니다.2.2.10에서 당일 주문 조회의 실제 출력 구조를 대조할 수 있도록231을 추가했습니다. 고정된 정의 파일만 읽으며 계좌 조회·주문 호출, 로그·설정·주문 저널 수집이나 자동 업로드는 하지 않습니다. 실제 파일을 확인해야 현재 설치의 형식과 입력 항목을 검증할 수 있습니다.

2.2.4는 주문 응답의 오류코드·상세 메시지를 콜백 안에서 수집하고 자격정보를 가린 뒤 주문 기록·화면에 보존합니다. 이전 버전은 오류상태와 출력0만 읽어 `거절`로 표시했고 상세 사유를 남기지 않았습니다. 이미 저장된 거절 기록의 원인을 소급해 복원할 수는 없습니다. 당시 사용자 HTS/MTS에서 두 매도 접수가 없었다는 확인을 받았고, 그 과거 실패의 원인은 소급 확인되지 않았습니다. 이후2.2.6의 매도1건 접수 확인과 구분합니다. 매수·매도는 같은 주문 API를 사용하지만 매도1건 접수 확인만으로 매수의 실서버 성공을 확인했다고 표시하지 않습니다.

설치된 `SABA101U1`/`SABA102U1` XTR의 구조를 읽어 구형6출력과 SOR/KRX/NXT/ORC 신형8출력을 구분합니다. 신형 KRX 전송 코드는 설치 Helper의 명시적 매핑으로만 선택합니다. 주문 정의·KRX 코드가 미확인이면 전송 전에 사유를 기록합니다. 출력1을 무조건 주문번호로 취급하지 않고, 복수 거래소 번호·KRX 경로 불일치·미확인 응답은 결과 불명으로 보존합니다. 이 형식 호환성과 진단 수정이 현재 사용자 설치의 접수 실패 원인을 해결했다는 뜻은 아닙니다.

`주문·체결`에서 행을 선택하면 아래 상세창에 응답 사유가 표시됩니다. 거절된 신규 요청을 실제 미체결 수량으로 표시하지 않습니다.2.2.9의 자동 재검증은 기존 거절 기록을 보존하고 새 감사 키로 현재 주문을 검증합니다. 명시적인 미접수 거절 근거가 없으면 일반 자동 재시도는 차단하며, 과거 사용자 확인을 적용하는 제한된 매도 재평가와 구분합니다.

2.2.3은 실제 화면의 두 보유 종목이 `현물 잔고구분 확인 대기`에 머문 문제를 다룹니다. 기존 반복3의 `보통` 문자열·반복22의 명시적인0이 없을 때는 공식 `SABA609Q1`의 입력3=`5: 보통잔고`를 별도 조회합니다. 전체 입력 설정 성공·정상 응답 연결을 확인한 뒤, 매매기준 잔고와 종목·수량·평단·주문가능수량·미체결이 일치하는 종목에 한해 현물 구분의 근거로 사용합니다. 매도수량은 매매기준 응답에서 가져오며 보통잔고 조회로 덮어쓰지 않습니다. 신용 구분·양수/비정상 융자금액·불일치·미검증/오래된 응답은 거부합니다. 주문 직전 두 잔고의5초 유효기간과 계좌 변동 이후 재조회 조건을 유지합니다.

`현물 구분 N/N`과 구분·융자 필드의 제한된 진단을 추가했습니다. 매수 후보는 실제 시세를 받은 뒤에도 같은 `시세 대기` 문구를 남기지 않고, `현재가/돌파기준 미돌파`, `누적거래량/기준 미달`, `매수 조건 충족` 등 실제 판단을 표시합니다. 전략 조건과 비율을 바꾸거나 조건과 무관하게 주문하지 않습니다. 실제 서버에서 새 보통잔고 조회·주문·체결이 완료됐다는 뜻은 아닙니다.

2.2.2는 실제 사용자2.2.1 화면의 **SC 콜백475회·장구분1·체결시각digits8 거부**를 수정합니다. 8자리 숫자의 명시적 `HHmmssff`와 `00HHmmss` 표현을 지원하며, 시·분·초와 정규장 시각 범위를 검증해 유일한 해석만 사용합니다. 예를 들어 `10045512`와 `00100455` 모두 실제 문자열의 `10:04:55`를 보존합니다. PC 시각에 맞는 임의의 부분문자열을 고르지 않습니다. 공식 설명은 필드 길이8까지만 제공하므로 이 두 표현 중 사용자 설치의 정확한 표현은 원본 값으로 확인해야 합니다. 정확히8개 ASCII 숫자인 공개 SC 시각만 화면·진단에 남기며 계좌 이벤트 원문은 기록하지 않습니다.

유효한 `HHmmss`와 `HH:mm:ss`도 계속 지원합니다. 화면·진단 로그에서 SC 콜백 수, 미수신, 시각 형식, 장구분, 첫 체결·연속 수신 대기, 시각 불일치·수신 지연을 구분합니다. 장중 등록 종목이 있는데 확인 수가0이면 빨간색으로 표시합니다. PC 시각으로 체결시각을 만들거나 정규장·연속 수신·45초 신선도 검사를 생략하지 않습니다.

2.2.0은 개장 전에 완료 일봉으로 이동평균·돌파 기준·평균 거래량을 준비하고 개장 때 그 자료를 그대로 사용합니다. `실주문 운영 시작`을 누르면 목표 거래일00시 이후 자동 분석하며, `전체 스캔`으로 주문 승인 없이 먼저 준비할 수도 있습니다. 처음 계좌를 연결해도 같은 목표일·전략·종목 목록에 맞는 공개 분석 자료는 보존합니다. 계좌·주문·시세·실주문 승인은 복원하지 않습니다.

개장 후에는 기존 보유와 준비 후보의 실제 SC 가격·당일 누적 거래량으로 판단합니다. 전일 신호 날짜를 오늘로 바꾸지 않으며, 주문 직전 당일 일봉 거래일·새 계좌 자료 검사는 유지합니다. 분석이 덜 끝났다면 완료 자료와 잔여 대기열을 보존하며 준비된 종목을 먼저 확인합니다. 같은 날 전체 일봉을20분마다 다시 조회하지 않습니다. 실시간200종목 한도에서 기존 보유·미완료 주문을 우선하고 나머지 감시목록을 순위화하므로 모든 준비 종목이 동시에 감시되는 것은 아닙니다.

`조회 전용 현재가`는 체결시각을 제공하지 않는 조회입니다. `실시간 SC` 확인 수와 `잔고 검증`을 별도로 표시합니다. **응답 구분값이 반드시1이어야 한다는 과잉 조건은 제거했습니다.** 실제 전송된 전체 매매기준 요청·설정 성공·요청번호·정상 수신을 확인해 잔고를 사용합니다. 구분값의 공란·0·미상은 진단으로 남기고, 명시적인 다른 잔고 기준과 모순되는 응답은 계속 거부합니다. 실제 금액·매도가능수량·현물 구분·미체결 대사·장중 시세 검사는 유지합니다. 장전 준비나 데이터 일치를 실제 서버 주문 성공·수익성 검증으로 부르지 않습니다.

2.1.2는 계좌 응답을 처음 받으면 CSV를 바로 저장하고, 조회·주문 준비가 대기 중이어도 주기적인 보고서 저장이 밀리지 않도록 수정합니다. `보고서 폴더`는 현재 계좌 자료를 즉시 저장한 뒤 폴더를 엽니다. 화면에 실제 저장 시각·파일명 또는 실패 사유가 표시됩니다. 계좌를 아직 조회하지 않았다면 가짜 빈 보고서를 만들지 않으며, 재시작 후에는 기존 보고서가 있는 폴더를 찾습니다. 파일 형식은 엑셀로 열 수 있는 `.csv`입니다.

과거2.1.1은 정상 수신 뒤 잔고 전체를 버리던 회귀를 고쳤지만 응답 구분값을 과도하게 요구해 주문이 계속 막힐 수 있었습니다.2.2는 이 조건을 위의 실제 요청·응답 확인으로 교체합니다. 읽을 수 있는 잔고·손익 표시, 선택 필드 공란 처리와 현재가 방향 부호 처리도 유지합니다.

**`실주문 운영 시작`을 누른 계좌에서는 주문별 데이터 조건을 통과하면 실제 신규·정정·취소 요청이 전송될 수 있습니다.** 앱 실행, 계좌 조회와 `전체 스캔`만으로 실주문을 시작하지 않습니다.2.0의 상시 비활성화 조건을 제거하고 계좌·거래일에 한정된 실행 세션과 주문 직전 검사를 사용합니다. 이 코드 변경을 실제 신한 서버의 주문·체결 검증 완료로 표시하지 않습니다.

## 실행 순서

1. [PR #1](https://github.com/na999jason-sketch/shinhan-autotrader/pull/1)의 **2.2.10 Windows 빌드 결과**를 확인하고 성공한 실행의 `ShinhanNativeTrader-Win32` ZIP을 받아 압축을 풉니다. 같은 실행의 `validation-reports`가 빌드·검증 기록입니다.
2. `전략·운용한도`에서 전략과 **0원보다 큰 실계좌 운용한도**를 정하고 `전략·운용한도 저장`을 누릅니다. 한도의 초기값은0이며 실제 예수금·주문가능금액을 대신하지 않습니다.
3. 공식 Indi를 실행·로그인한 뒤 `Indi 연결·종목 조회`로 종목 수신을 확인합니다. EXE의 관리자 권한 확인은 Windows가 처리합니다.
4. 계좌번호·계좌암호를 프로그램에 입력하고 `실계좌 조회·감시`를 누릅니다. 계좌 조회와 공개 종목 분석이 자동으로 시작됩니다. `실계좌 잔고·손익`의 `매도판정`·`매도 주문상태`와 `주문·체결`에서 조회값과 시각을 확인합니다. 과거 접수 주문은 정상 당일 조회로 대사하며, 조건이 맞으면 `증권사 전량체결 대사 완료`로 표시합니다. 이번 확인구분 충돌은 아직 대사 대기로 남습니다. 이 버튼은 실주문을 시작하지 않습니다.
5. 해당 계좌의 자동 주문을 실행하려면 **`실주문 운영 시작`**을 누릅니다. 목표 거래일00시 이후 사전분석하고, 개장 후 실제 시세·계좌 확인을 거쳐 판단합니다. 이미 장중이면 준비된 종목부터 실시간으로 확인하며 남은 분석을 이어갑니다. 거절 주문도 조건과 한도 안에서 자동 재검증하므로 별도 선택 재시도 조작은 필요하지 않습니다. 화면에서 분석 진행·실시간 수신·주문 대기 사유를 구분할 수 있습니다.
6. `보고서 폴더`에서 날짜별 계좌·주문 기록을 확인합니다. 출근 전·퇴근 후 확인 항목은 [Windows 운영 안내](docs/USER_WINDOWS_VALIDATION.md)에 정리했습니다.

운용한도나 전략을 다시 저장하면 운영과 계좌 세션이 해제됩니다. 계좌암호를 다시 입력해 `실계좌 조회·감시` 후 `실주문 운영 시작`을 눌러야 합니다. 암호는 실행 세션 메모리에만 유지하고 설정·보고서·주문 저널에는 저장하지 않습니다.

## 자동 운영과 중단

주문 운영시간은 한국시간 **평일09:00~15:20**입니다. 사전분석은 목표 거래일00시 이후 완료 일봉으로 순차 진행합니다. 개장 전 준비가 끝나도 실제 주문은 개장 후 진행하는 SC 시세·거래량과 모든 계좌 검증이 필요합니다. 모든 종목의 모든 틱을 동시에 수신하는 방식은 아니며 휴장일 달력은 아직 연동하지 않았습니다. 설정 저장·중단·연결 변경·목표일 변경으로 준비를 무효화하고 재시작 후 분석 자료를 디스크에서 복원하지 않습니다.

기존 보유와 새 보유에 같은 손절·익절·추적손절 규칙을 적용합니다. 기존 보유를 개장 시 일괄 매도하지 않습니다. 매도 접수 금액을 가용자금으로 더하지 않으며, 다음 매수에는 실제 계좌의 주문가능금액·종목별 가능수량을 새로 확인합니다.

실주문 시작 상태는 **한 계좌·한 거래일**에 한정되며 디스크에 저장하지 않습니다. 장외에 시작하면 다음 평일을 대상으로 하고 해당 거래일15:20에 만료됩니다. 다음 거래일에도 주문하려면 다시 시작해야 합니다. 만료 후에도 계좌 조회·실시간 수신·기존 주문의 후속 체결 확인·보고서는 계속합니다.

**`운영 중단`, 앱 종료·재시작·연결 단절은 추가 주문 전송을 막으며 이미 증권사에 접수된 주문을 자동 취소하지 않습니다.** 남은 주문은15:20 이후에도 체결될 수 있습니다. 접수된 주문의 취소·확정 상태는 `주문·체결`과 HTS에서 별도로 확인해야 합니다. 미확정 주문을 재시작 후 자동 재전송하지 않습니다.

2.2.8에서는 불명 주문이나 실시간 수신 오류로 인한 자동 일시 중단이 조회용 계좌 세션까지 해제하지 않습니다. 계좌 조회·감시·보고서는 계속하며, 대사 결과와 실패 사유를 표시합니다. 사용자의 `운영 중단`·앱 종료는 계좌 세션을 해제합니다. 대사 완료는 실주문 재시작 승인이 아닙니다.

자동 운영 중에는 Windows 자동 절전을 억제하고 중단·종료 시 해당 요청을 해제합니다. PC 전원·네트워크·Indi 로그인이 유지돼야 하며 수동 절전·OS 재시작이나 인증 만료 후 자동 로그인은 제공하지 않습니다.

## 주문별 실행 조건

매 주문은 시작된 계좌 세션, 운용한도, 실제 조회와 실시간 수신을 대조합니다. 주요 조건은 다음과 같습니다.

- 시각이 진행하는 정규장 SC 시세2회 이상과 해당 종목의 당일 일봉 거래일을 확인합니다. 수동 현재가 조회의 수신 시각을 체결시각이나 거래일로 사용하지 않습니다.
- 체결기준 실제 잔고·현금100% 주문가능금액·당일 주문을 새로 확인합니다. 매수는 종목별 비율100 가능수량·가능금액, 매도는 현물 보유와 주문가능수량을 확인합니다.
- 프로그램이 아는 주문·개별 체결과 누적 조회 수량을 대조합니다. 정상 접수 원주문의 전량체결 체크포인트는 검증된 조회 근거로 별도 보존하며, 기존 개별 체결을 중복 합산하지 않습니다. 불명 주문, 프로그램 외 미체결, 중복 주문, 수량 불일치·시세 누락·한도 부족은 해당 주문을 차단합니다.
- 조회 이후 계좌 이벤트로 데이터가 바뀌면 다시 조회합니다. 실제 `RequestData` 호출 직전에도 실행 세션과 데이터 변경 여부를 재검사합니다.

이는 구현된 실행 조건이며 현재 서버의 의미와 전체 체결 복구가 독립적으로 인증됐다는 뜻은 아닙니다. 상세 근거는 [실시간 계약](docs/INDI_REALTIME_CONTRACT.md), [주문 계약](docs/INDI_LIVE_ORDER_CONTRACT.md), [현재 인터페이스 확인 범위](docs/INDI_API_VERIFICATION.md)에 있습니다.

## 손익과 저장

평가손익은 실제 수량·평균단가·조회 가격으로 계산하며 **수수료·세금 제외**입니다. `실현손익(증권사 조회)`는 SABA609Q1의 응답값과 조회 시각을 표시합니다. 원천 거래일이 확인되지 않으면 이를 당일 확정 실현손익으로 부르거나 PC 날짜로 보완하지 않습니다. 주문 접수와 누적 체결 조회를 가상 체결로 바꾸지 않습니다.

| `live-orders-<계좌키>.xml` | 거래일·계좌 식별 지문·주문 중복방지·확인된 접수/체결/취소 상태·개별 체결과 구분된 누적 체결 체크포인트 |
| `reports\<계좌키>\account-report-yyyyMMdd.csv` | 실제 조회와 손익, 증권사 주문 스냅샷, 주문 상태·조회 시각 |
| `diagnostics.log` | 민감정보를 가린 진단 기록 |

계좌키에 계좌번호를 그대로 쓰지 않으며 보고서에 계좌번호·암호를 넣지 않습니다. 보고서는 보유 수량·가격 등 투자 정보를 포함합니다. 설정과 주문 저널은 원자적으로 저장하며 미완료·불명 주문은 증권사 증거 대사 없이 정상/체결완료로 바꾸지 않습니다. 과거 `paper-v2.xml`은 읽거나 실계좌로 변환하지 않으며 [이전 엔진](legacy/paper/README.md)은 EXE에서 제외돼 있습니다.

## 확인된 결과와 남은 실제 검증

사용자1.4.x 화면에서 종목4,330건·일반주식2,401개, 수동 현재가 응답, 일봉45개 반복 수신, 잔고2건과 스캔262개·후보2개를 확인했습니다. 이는 응답 수신·파싱·표시 증거이며 HTS 대조나 주문 체결 증거는 아닙니다.

**사용자2.2.6 실행의 실제 매도 접수1건은 확인됐습니다.** 접수 직후 실시간 장애와 운영 중단이 관측됐으며, 개별 체결·누적 수량·잔고 반영의 완전한 대사는 아직 확인되지 않았습니다. 실제 매수·정정·취소·부분체결 처리·재시작 복구·무인운영도 남은 검증입니다. 이 작업의 도구로 실제 계좌 주문을 실행하지 않았습니다. CI의 단위·가짜 전송·합성 COM·Windows UIPI·GUI 검증은 코드 동작을 검사하며 실제 서버 종단 간 검증이나 수익 검증을 대신하지 않습니다. 최신 빌드 결과와 EXE 링크는 PR에서 확인하십시오.

사용자2.2.7의 정상 종목·계좌·주문 조회도 확인됐지만 기존 불명 주문 때문에 운영이 중단됐습니다.2.2.8의 전량체결 체크포인트 복구는 합성 검사로 검증했으며 **실제 Windows Indi 서버에서의 복구 완료는 아직 미검증**입니다. 조회 행수 감소만으로 전량체결을 확정하거나 실시간 장애가 해결됐다고 표시하지 않습니다.

2.2.9의 자동 거절 재검증·제한된 과거 매도 재평가도 합성 검사와 실제 서버 검증을 구분합니다. 실제 서버에서 자동 재검증 후 주문·체결이 완료됐다는 증거는 아직 없으며, 최초 AA·AD 실시간 오류의 원인이 해결됐다고 보고하지 않습니다.

2026-11-13 첨부 CSV에는 기존 접수 주문의 누적 전량체결 수량·평균가와 확인구분`1`이 함께 있습니다.2.2.10은 이를 `전량체결 수량·확인명세 충돌`로 구분하며 실제 복구 완료를 주장하지 않습니다. 최신 CSV는 거부코드·거부명 유무와 상태명 등을 제한된 분류로 추가 기록합니다. 새 설치 정의와 이 분류를 대조하기 전에는 확인구분의 서버 의미나 실제 출력 구조 차이를 확정할 수 없습니다.
