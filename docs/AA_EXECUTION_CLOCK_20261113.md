# AA 체결시각과 운영 중단 수정 — 2.2.12 / 2026-11-13 KST

2.2.12는 실제 매도 체결 통지의8자리 시각을 거부하던 AA 파서를 수정한다.15:16:40의 장애는 프로그램이 AA 체결시각을6자리로만 해석한 문제다. 체결을 복구하는 당일 조회는 정상적으로 계속됐지만, 이미 해제된 주문 승인은 자동으로 복원되지 않아 이후 매수도 전송할 수 없었다.

## 실제 기록에서 확인한 경과

사용자가 제공한 전체 진단과 후속 CSV를 대조했다. 원본 로그·계좌번호·암호·사용자 경로는 이 문서에 복사하지 않는다.

| 한국시각 | 확인된 동작 |
| --- | --- |
| 15:16:40 | AA 실시간 처리에서 필드25·`InvalidClock`·`Digits8` 실패가 발생했다. 주문이`Unknown`으로 전환되고 주문 승인이 해제됐다. |
| 15:16:44 | 정상 당일 주문 조회의 전량체결을 대사해 해당 주문을`Filled`로 복구했다. 주문 승인은 해제된 상태를 유지했다. |
| 이후~15:26 | 계좌·일봉 조회 등 읽기 작업이 계속됐다. 조회가 계속됐다는 사실은 실주문 승인이 유지됐다는 뜻이 아니다. |

후속 CSV에서는`069500`2주가 평균83,775원,`305720`8주가 평균12,730원으로 전량체결됐고 두 프로그램 기록도`Filled`임을 확인했다. 이는 당일 누적 조회와 프로그램 복구의 증거다. 이번에 실패한 개별 AA 체결 이벤트가 당시 정상 반영됐다는 증거로 사용하지 않는다.

기존 파서는 AA의 체결시각 필드25에`HHmmss`6자리를 요구했다. 실제 실패 자료의 값 형식은`Digits8`이었다. 따라서 이번 중단 원인은 프로그램의 시각 형식 처리로 특정됐다. 이전에는 정상일 수 있는8자리 값을 오류 검사 사례로 두어 이 잘못된 가정을 테스트가 고정하고 있었다.

이 장애는15:16:40 이후 주문 승인이 해제된 이유를 설명한다. 그 이전의 개별 후보가 매수되지 않은 이유까지 이 오류 하나로 단정하지 않는다. 당시 후보별 돌파·거래량·최신 SC·계좌 조건은 별도 판단이다.

## AA 전용 시각 처리

새`NormalizeExecutionClock`은 AA 체결에 한정해 다음 표현을 처리한다.

| 표현 | 처리 |
| --- | --- |
| ASCII 숫자6자리`HHmmss` | 기존의 유효한 시·분·초 해석을 유지한다. |
| ASCII 숫자8자리`HHmmssff` | 앞6자리를 명시적인 시·분·초로 검증하고 뒤2자리의 원래 정밀도는 원문에 보존한다. |
| ASCII 숫자8자리`00HHmmss` | 앞의 리터럴`00`과 뒤6자리 시·분·초를 검증한다. |

8자리 해석은 기존의09:00~15:30 범위 시각 검증을 사용한다. 두 표현은 이 범위에서 서로 다른 시각으로 겹치지 않으며, 임의 부분문자열이나 PC 수신시각을 보고 해석을 선택하지 않는다. 잘못된 시·분·초·길이·비ASCII 숫자·문자는 거부한다. AA의 콜론 표현은 실제 관측되지 않았으므로 지원 범위에 추가하지 않았다.

실제 진단은 원래8자리 값 자체를 저장하지 않고 고정된 형식 분류만 남겼다. 따라서 사용자 서버가 위 두8자리 표현 중 어느 것을 보냈는지는 아직 확정하지 않는다. 이번 수정은 두 명시적 표현을 모두 검증하며, 임의 숫자8자리를 정상 시각으로 받아들이는 처리가 아니다.

## 체결 원문과 식별 근거 보존

AA DTO의`OriginalClock`에는 검증된 원래 시각 문자열을,`Clock`에는 정규화한6자리 시각을 보존한다. 파서와 라우터의 메모리 복사·접수 응답 전 버퍼에도 두 값을 함께 유지한다. 원래 시각 문자열을 진단 로그에 추가하지 않는다.

체결번호22·개별 체결수량23·체결가격24·수신 UTC는 그대로 유지한다. 시각 문자열로 체결번호를 만들거나 새로운 거래일·체결일을 합성하지 않는다. 저널의 관측 UTC를 증권사 체결시각으로 바꾸지 않으며 수량·평균가·체결금액을 시각 보정으로 변경하지 않는다.

라우터는`OriginalClock`이 있으면 같은 AA 정규화로 얻은 값이`Clock`과 일치하는지 다시 검사한다. 원문과 정규화 값이 모순되거나 잘못된 원문을 정상6자리로 대체한 DTO는 차단한다. 이전의`OriginalClock` 없는6자리 DTO 호환성은 유지한다. 접수 전 버퍼는 방어적으로 복사하고, 같은 실제 체결번호의 중복 통지는 다시 합산하지 않는다.

시각을 읽었다는 이유만으로 체결을 확정하지 않는다. 기존의 계좌·상품·주문번호·처리구분·수량·가격·정상 접수·원주문 관계·기존 체크포인트 대조를 유지한다. 지원하지 않는 시각이나 모순된 체결은 계속 오류·대사 대상으로 처리한다.

## 회귀 검사와 실제 적용 범위

기존2.2.11에서는 정상적인 두8자리 AA 사례가 실패했다. 새 검사는 두 표현과 기존6자리의 정상 파싱, 원문/정규화·체결번호/수량/가격/수신시각 보존을 확인한다. 잘못된 시각·길이·문자·지원하지 않는 콜론 표현은 여전히 실패해야 한다.

라우터는 정상 접수 뒤8자리 AA를 실제 체결번호로 반영하는 경로, 중복 멱등성, 이미 누적 체크포인트에 포함된 지연 이벤트, 접수 전 버퍼 복사와 원문/정규화 충돌을 검사한다. 실제 폼 검사에서는 정상 접수→AA8자리→`Filled` 뒤 주문 승인이 유지되고 후보 평가가 계속되는 흐름을 확인한다. 합성 검사 수와 Windows 빌드 결과는 [TEST_REPORT.txt](../TEST_REPORT.txt)와 [PR #1](https://github.com/na999jason-sketch/shinhan-autotrader/pull/1)에 기록한다.

**사용자 Windows Indi 서버에서 새 EXE가8자리 AA를 정상 처리했는지는 아직 미검증이다.** 기존 두 매도의 실제 전량체결과 조회 복구는 확인됐지만, 이 코드의 실제 AA 수신·후속 매수·정정·취소·부분체결·재시작·전체 무인운영이 모두 검증됐다는 뜻은 아니다. 이 작업의 도구로 실제 계좌 조회나 주문을 실행하지 않았다.

## 새 버전 사용과 매수 조건

성공한2.2.12 Windows 빌드를 실행하고 Indi 연결 후`실계좌 조회·감시`로 현재 계좌와 주문 상태를 확인한다. 미확정 주문 대사가 완료돼 운영 가능한 상태이면`실주문 운영 시작`을 누른다. 복구만으로 주문 승인을 자동 복원하거나 과거 주문을 재전송하지 않으며, 기존 거절 행의 수동 재시도는 필요하지 않다.

매도 후 즉시 매수하거나 거래 건수를 만들기 위해 매수하지 않는다. 매수는 준비 후보의 실제 최신 연속 SC, 당일 돌파·누적 거래량, 가격 범위·운용한도·주문가능금액/수량 등의 조건을 계속 요구한다. 후보별 상태는`발굴 후보`에서 확인한다. 신규 주문 운영시간은 한국시간 평일09:00~15:20으로 유지한다. AA8자리의15:30까지 시각 해석은 기존 접수 주문의 체결 수신을 위한 것이며 신규 주문 운영시간을 연장하지 않는다.
