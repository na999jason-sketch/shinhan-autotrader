# Indi 인터페이스 확인 기록 — 2.1

공식 자료의 정적 대조, 프로그램이 실행 중 검사하는 조건, 실제 Windows/서버에서 확인한 결과를 구분한다.2.1은 사용자 계좌·거래일에 한정된 실주문 시작 세션을 제공한다. 상시 `false` 조건을 제거했지만 실행 중 수집한 값의 일치 검사를 공식 인증이나 실제 주문 성공으로 취급하지 않는다. 이 작업의 도구로 실제 신한 계좌 주문을 실행하지 않았다.

현물 계좌용은 AA·AD다. AB·AE는 파생상품용이며 현물 체결이나 잔고 검증을 대신하지 않는다.

2.1 사용자의 실제 화면에서는 `ReceiveData` 오류상태0 뒤 반복2 값에 대한 앱의 엄격한 비교가 예외를 내 전체 조회가 중단됐다. 공식 Helper/XTR의 반복2는 구분코드 폭1이며 `1` 매매기준 설명은 서로 일치한다. 사용자의 실제 필드값은 화면에 없으므로 다른 코드를 매매기준으로 추정하지 않는다.2.1.1은 행별 기준과 전체 계좌의 기준 증명을 따로 보관하고, 알려진 코드·공란·미상을 고정된 분류별 개수로만 기록한다. 미상·누락을 실제 신용 수량으로 꾸미지 않는다. 선택 손익·융자 증명 필드가 누락돼도 읽을 수 있는 잔고를 버리지 않으며 필수 수량·코드 오류는 계속 거부한다.

빈 잔고는 전체 출력이 설정된 매매기준 요청, 조회명 대조, 입력 성공, 요청번호가 일치하고 오류상태가 없는 응답 문맥으로만 범위를 확인한다. 이 문맥은 반환된 구분값 원문을 바꾸지 않으며 명시적인 상충 기준을 거부한다. 빈 잔고에 보유 수량이나 체결을 만들어 넣지 않으며 현금·가능수량·주문 대사와 거래일 조건은 별도로 검사한다.

2.2는 위2.1.1의 반복2 엄격 일치 조건을 교체한다. 실제 전송 입력의 비공개 복사본에서0~6번 전체 필드와 계좌·암호 형식, 상품01·매매기준1·평균단가1·ELW제외1·전체출력0을 확인한다. 모든 setter의 명시적 true, 쿼리명 대조, 양수 요청번호와 일치 콜백의 오류상태0이 있어야 빈 잔고와 비어 있지 않은 잔고 모두 주문 근거가 된다. 구분값1만 반환됐다는 이유로 미연결 요청을 승인하지 않는다. 공란·0·미상 응답 구분값을1로 바꾸지 않으며 진단에 그대로 분류하고, 명시적인 다른 기준2·3·4·5는 계속 거부한다. 실제 입력 설정에 따른 조회 의미를 사용하는 구현이며 최신 서버의 전체 금융 의미를 독립적으로 인증한 결과는 아니다. 설치된 `qry/saba609q1.xtr`의 크기·SHA256·참조 일치 여부도 읽기 전용 진단으로 남기고, 원본 정의·경로·계좌정보는 덤프하지 않는다.

## 날짜와 손익의 범위

`SABA609Q1` 단일0은 추출 XTR에서 폭2인 날짜 항목이다. 이를 현재 PC의 연·월과 조합해 증권사의 전체 거래일로 만들지 않는다.2.1은 실시간 구독 세션 이후 새로 요청한 해당 종목 `TR_SCHART`의 실제 `yyyyMMdd`가 현재 KST 거래일과 일치하는지 별도로 검사한다.

609 실현손익 단일16은 실제 응답값으로 보관한다. 화면의 `실현손익(증권사 조회)`에 조회 시각을 붙이되 원천 거래일을 확인하지 못한 값을 당일 확정 손익으로 부르지 않는다. 보고서도 원천 날짜가 불명확하면 그 범위를 미확인으로 남긴다. 평가손익·평가수익률은 실제 보유 수량·평단·조회 가격으로 계산하며 수수료·세금을 제외한다.

## 실행 중 주문 조건

1. 사용자가 앱의 `실주문 운영 시작`을 선택한 계좌와 대상 거래일이어야 한다. 양수 운용한도가 필요하며15:20에 만료된다. 중단·재시작·계좌/연결 변경으로 해제되고 자동 복원되지 않는다.
2. 해당 종목의 정규장 SC 시각 진행과 시세 나이, 실시간 세션 이후 새로 받은 당일 일봉 날짜를 확인한다. 등록 bool이나609의 짧은 날짜만으로 충족시키지 않는다.
3. 새로운 체결기준 보유·현금·주문 응답을 사용한다. 매수는 비율100 종목별 가능금액/수량과 운용한도·예약금을, 매도는 보통 현금 보유·주문가능수량을 검사한다.
4. 알려진 로컬 주문과 실제 누적 주문 행, 고유 개별 체결 ID·수량을 대조한다. 프로그램 외 미체결, 미확정/불명 주문·누적 불일치·중복 키는 차단한다. 로컬 미완료가 없는 기준 상태와 알려진 주문/체결의 대사는 범위를 구분하며 계좌 전체의 독립적인 감사 완료로 표시하지 않는다.
5. AA/AD 등으로 계좌 데이터가 바뀌면 이전 조회를 무효화한다. 어댑터의 실제 `RequestData` 직전에도 계좌·거래일 세션과 데이터 변경 번호를 다시 검사한다. 검사 도중 바뀌거나 근거가 사라지면 전송하지 않는다.

이 조건은 코드상의 수용 기준이다. 같은 출처의 수량이 일치했다는 사실만으로 최신 서버 필드의 금융 의미, 수수료·예약금 반영이나 조회 완결성이 독립적으로 인증됐다고 주장하지 않는다. 현재 일반 현금 경로의 상품·호가 규칙 범위 밖은 추정해 보내지 않는다.

## 중단·복구와 남은 실제 검증

시작 상태 만료·중단은 추가 전송을 막고 이미 접수된 주문을 자동 취소하지 않는다. 만료 뒤 기존 주문은 추가 체결될 수 있다. 재시작 시 미완료 주문은 불명 상태로 보존하며 확인되지 않은 주문번호·수량·체결을 만들어 복구하지 않는다. 정정/취소 요청과 확정, 역순·중복·누락과 외부 수동 거래는 별도 상태로 다룬다.

사용자1.4.x 화면에서는 종목4,330건·일반주식2,401개, 수동 현재가, 일봉45개, 실제 잔고2건과262개 분석·후보2개를 확인했다. 이는 수신·파싱 증거이며 HTS 일치·실제 주문·부분체결·장애 복구의 검증 결과가 아니다.

2.1의 실제 신한 서버 종단 간 신규·정정·취소·체결·복구는 아직 미검증이다. 최신 시장 라우팅·프로그램매매 필드·상품별 호가, 금액의 비용/예약금 의미, 계좌 이벤트 누락과 조회 완결성, 서버 날짜·실현손익 기간도 실제 설치/HTS 대조가 남아 있다. CI의 가짜 전송·합성 COM·GUI 테스트는 코드 증거이며 실제 돈을 쓰는 주문을 실행한 증거가 아니다.

기존 Python 경로는 별도 구버전이다. Python API의 주문 차단 테스트를 유지하지만2.1 C# 실주문 시작·실행 정책과 혼동하지 않는다. 최종 CI·EXE 링크와 변경별 검증 결과는 [PR #1](https://github.com/na999jason-sketch/shinhan-autotrader/pull/1)과 [검증 보고서](../TEST_REPORT.txt)를 참조한다.
