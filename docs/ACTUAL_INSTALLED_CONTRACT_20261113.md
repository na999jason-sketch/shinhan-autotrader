## 확인된 차이와 적용

직렬화 식별자가 구형0x0207에서 현재0x0208이다. 현재 두 주문 정의의 폴더·필드 레코드를 구조적으로 읽었고 파일 끝까지 남은 바이트가 없음을 검사했다. 신규 주문은39입력/8출력, 정정취소는38입력/8출력이다. 구형 주문 정의의36입력/6출력·35입력/6출력도 별도로 유지한다.

| --- | ---: | ---: |
| 조건가격 | SI36 | SI36 |
| 주문방식 구분 | SI37 | SI35 |

Helper는 정정취소SI35에 `0:SOR 1:KRX 2:NXT`를 명시한다. 신규SI37의 설명은 비어 있지만, 두 실제 XTR가 같은 레이블 `주문방식구분코드`·내부 별칭 `ord_meth_tp_code`·문자형9·폭1을 가진다. 이 동일 도메인과 상대 정의 전체의 정상 인식을 함께 검증할 때만 신규에도 KRX1을 연결한다. 누락·별칭/폭/형식 차이·중복·상충 매핑은 거부한다. 숫자0을 KRX로 추정하지 않는다. 일반 KRX 지정가는 조건가격과 SOR원주문번호를 빈 값으로 설정한다.

609 잔고는 입력7 `조회시세구분코드`가 추가돼 총8입력이다. Helper에 `0:통합시세 1:KRX시세(NULL일시 KRX시세)`가 명시돼 있어 앱은1을 설정한다. 매매기준과 보통잔고 조회 모두8개 전체 입력·setter 성공·양수 요청번호·정상 일치 콜백을 요구한다. 공란의 KRX 기본값도 설명돼 있으므로 이전 누락이 GI004의 원인이라고 확정하지 않는다.

## 검증 범위

- 실제 첨부 신규·정정취소 XTR를 각각2384/2344바이트 끝까지 읽어 Modern·KRX1로 판정했다. 구형 공식 배포 정의도 그대로 Legacy로 판정했다.
- 실제 첨부 정의를 파서에 넣은 뒤 순수 요청 생성기로 매수·매도·정정·취소의 KRX1과 빈 조건/SOR 항목을 확인했다. 계좌·주문 객체는 합성 값이며 전송하지 않았다.
- 합성 네이티브/GUI/단위 검증과 실제 금융 서버 검증은 구분한다. 실제 GI004 재발 여부, 요청 접수·체결·잔고 반영과 현재 거래소/복구 의미는 사용자 Windows에서 확인해야 한다.
