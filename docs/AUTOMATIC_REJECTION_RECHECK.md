# 거절 주문 자동 재검증 — 2.2.9

실주문 운영 중 현재 전략의 당일 매수·매도 주문이 명시적인 미접수 거절로 끝났다면, 프로그램이 기다렸다가 새 조건으로 다시 검토한다. 일반 화면에서 행별 재시도 버튼을 누르는 절차는 제거했다. 이 기능은 접수·불명 주문을 다시 보내거나 과거 주문을 그대로 복사하는 기능이 아니다.

## 대상과 제한

일반 자동 재검증에는 보존된 요청번호·인식된 응답 형식·거절 판정과 **거래소 주문번호 필드의 명시적인0**이 필요하다. 신형 응답에서는 SOR·KRX·NXT 세 필드 모두0이어야 하며 공란·누락·판독 실패는 이 근거가 아니다. 공급자 오류 플래그가 있어도 이 조건을 모두 충족하면 재검토할 수 있지만, 오류 플래그만으로 재시도를 허용하지 않는다. 숫자로 된 ORC 참조값은 거래소 접수번호로 바꾸지 않는다.

최초 주문 뒤 추가 전송은 **종목·매수/매도 방향·한국 거래일별 최대3회**이며, 직전 거절 후30·60·120초 대기를 적용한다. 과거 선택 재시도와 아래의 제한된 과거 매도 재평가도 같은 한도에 포함한다. 고유 감사 키와 횟수는 주문 기록에 보존해 재시작으로 초기화하지 않는다. 실주문 시작 승인은 재시작 후 다시 필요하다.

접수·체결·미체결 확인 중인 주문, 같은 종목의 미완료 주문, 결과 불명 주문은 자동 재전송하지 않는다. 장외·운영 중단·신호 해제·불일치·한도 도달도 전송 사유가 되지 않는다.

## 매번 새로 확인하는 근거

1. 거절 이후 시작한 정상 당일 주문 조회가 현재 계좌·거래일에 연결돼야 한다. 전체 요청 범위·입력 설정 성공·요청번호·정상 콜백·수신5초 이내를 확인하고, 같은 종목의 증권사 미체결이 있으면 차단한다.
2. 현재 완료봉·정규장 실시간 시세로 매수 돌파·거래량 또는 매도 손절·익절·추적손절 조건을 다시 평가한다. 대기 중 신호가 해제되면 준비 중인 주문도 취소하고 전송하지 않는다.
3. 새 매매기준·현물 잔고, 현금100% 주문가능금액, 매수 종목별 가능수량과 금액, 매도 가능수량·미체결·운용한도를 재검사한다. 과거 수량·지정가를 재사용하지 않는다.
4. 실제 요청 직전에도 계좌·운영 승인·신호·시세·재시도 근거와 감사 키를 다시 확인한다. 새 계좌 이벤트나 자료 변경이 있으면 다시 조회하며, 과거 거절 기록은 덮어쓰지 않는다.

화면에는 자동 재검증 대기·최신 계좌와 주문 조회 대기·전략 조건 미충족·당일 한도 도달을 구분해 표시한다. 대기시간이 끝났다는 이유만으로 주문을 전송하지 않는다.

## 과거 사용자 미접수 확인의 제한된 반영

사용자가 HTS/MTS에서도 주문이 없다고 확인한 과거 두 매도 기록에는 당시의 구조화된 접수 응답이 남아 있지 않다. 이 확인은 `UserConfirmedNoOrder`라는 **사용자 확인 근거**로 계좌·거래일·원본 기록별 저장하며, 증권사의 접수·거절 응답으로 만들지 않는다.

적용 범위는 당시 확인한 계좌의2026-11-13 종목코드`069500`·`305720`, 당일 전략 매도 원본 중 접수 응답·증권사 주문번호·체결·취소가 없는 거절 기록으로 한정한다. 원래 계좌 키를 한 번 더 해시한 값으로 현재 계좌를 대조하며 계좌번호나 원래 키를 저장소에 넣지 않는다. 현재 해당 종목을 보유하고 사용자가 실주문 운영을 시작한 경우에만 원본별1회의 새 전략 재평가를 허용한다. 시작 후 첫 잔고가 늦게 도착해도 같은 범위의 보유 확인을 이어서 적용한다. 수량·가격은 현재 실제 자료와 전략으로 정하며, 다음 거래일에는 이 일회 처리 때문에 일반 운영이 막히지 않는다.

첫 재평가가 실제 전송됐다면 다음 재시도는 그 새 주문의 명시적인 미접수 거절 근거가 있어야 하며 전체3회 한도를 지킨다. 다른 날짜·다른 종목·과거 매수·접수된 주문·불명 주문에는 이 처리를 적용하지 않는다. 원본 기록을 삭제하거나 접수된 주문을 다시 보내는 이관이 아니다.

## 실제 검증 범위

자동 재검증은 코드·합성 검사와 실제 서버 검증을 구분한다. 실제 서버에서 이 경로의 재검증 후 주문·체결이 완료됐다는 증거는 아직 없다. 기존 전량체결 복구와 실시간 오류 시 추가 주문 중단도 유지하며, 복구 후에는 명시적인 운영 재시작이 필요하다. 최초 AA·AD 오류의 원인은 아직 확정되지 않았다.
