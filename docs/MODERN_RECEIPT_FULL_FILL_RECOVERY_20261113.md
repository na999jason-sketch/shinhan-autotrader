# 현행 접수 상태와 전량체결 복구 — 2.2.11 / 2026-11-13 KST

2.2.11은 실제 설치의 당일 주문 조회 정의와 `접수` 상태를 함께 대조해, 기존에 정상 접수된 원주문의 누적 전량체결을 복구한다. 확인구분`1`을 정상코드`0`으로 바꾸거나 공식 열거 의미를 재정의하지 않는다. **실제 Windows Indi 서버에서 새 복구 경로가 완료됐는지는 아직 미검증이다.**

## 새 자료에서 확인한 사실

후속 사용자 CSV의 기존 매도 조회 행은 다음과 같다. 계좌번호·암호·사용자 경로·원본 공급자 메시지는 이 문서에 기록하지 않는다.

| 항목 | 실제 첨부 자료 |
| --- | --- |
| 기존 정상 접수 번호 / 증권사 조회번호 | `000000000000990516` / `990516` |
| 종목·방향 | `069500` / 매도 |
| 주문수량·지정가 | 2주 / 83,775원 |
| 누적 체결수량·평균체결가 | 2주 / 83,775원 |
| 미체결수량·확인수량 | 0주 / 0주 |
| 확인구분 `MO21` | `1` |
| 거부코드·거부코드명 형태 | `Blank` / `Blank` |
| 상태명 `MO31` | `접수` |

후속 XML의 실제 `saba231q1.xtr`는3,380바이트이며 SHA256은 `bc0a6e86f5850dbfdca351a0cb29d42e13ab9562862a96ef7b8c55fbe6c72e3b`다. 파일 끝까지 분석한 구조는`0x0208`·입력9·단일출력6·반복출력54다. 기존 반복0~40의 위치는 같고,41~53에 주문방식·SOR/NXT 등의 필드가 추가됐다. 따라서 이번 값이 필드 위치가 밀려 생긴 문제라는 가설은 배제했다.

실제 정의의 반복21은 `확인구분` / 내부명`ord_stat_tp_code`, 반복31은 `상태명` / 내부명`ord_proc_stat_nm`이다. 거부코드와 거부코드명은 별도의 반복19·20이다. Helper는 여전히 확인구분을`0 정상 / 1 거부 / 2 접속실패 / 3 거래소거부`로 안내하며 XTR 자체에는0/1의 열거 설명이 없다. 기존 코드는 이 Helper 안내를 모든 응답에 적용해, 실제 새 자료의`1 + 접수 + 거부정보 없음 + 전량체결` 조합도 거절로 분류했다.

## 현재 설치 정의에 한정한 상태 대조

실제 조회마다 등록된 Indi 설치의 고정`qry/saba231q1.xtr`를 읽는다. 바이트 내용을 보관·변경 가능한 외부 플래그로 대신하지 않고, 전체 구조의 쿼리 이름·직렬화 버전·입출력 그룹·필드 수와 **모든 레이블·내부명·자료형·폭**을 검사한다. 끝까지 읽히지 않거나 필드가 바뀐 정의는 현재 프로필로 인정하지 않는다. 인식된 정의는 변경할 수 없는 프로필 정보와 전체 파일 SHA256으로 조회 요청에 결합한다.

그 프로필은 요청의 전체 입력 설정 성공·정확한 계좌/당일 조회 범위·양수 요청번호·같은 요청의 정상 오류0 콜백을 확인한 뒤 반환 행에 사용한다. 이전 CSV를 읽어 저널을 바꾸거나 임의로 지정한 프로필 이름·해시만으로 정상 수신 증거를 만들지 않는다.

`ModernOrderState54` 프로필의 행 중 다음 조건을 모두 만족한 경우에만 확인 근거를 `StatusCorroborated`로 구분한다.

- 원래 확인구분은 정확히`1`이며 상태명은 정확히`접수`다.
- 별도 거부코드·거부명은 공란 또는0뿐이고 거부·접속실패 상태가 없다.
- 주문방식은 공란 또는 검증된 KRX 코드`1`이며, SOR 주문번호·SOR 원주문번호가 없다.

`StatusCorroborated`는 접수나 체결의 독립 증명이 아니다. 프로필이 검증되지 않은 구형 응답의`1`, 코드`2`·`3`, 다른 상태·거부정보·경로 불일치는 이 경로를 사용할 수 없다. `1`을`0`으로 정규화하지 않고 원래 코드와 출처를 보존한다.

## 전량체결 복구에 필요한 나머지 근거

상태 대조 후에도 기존 전량체결 복구 조건을 모두 검사한다.

- 프로그램이 정상 접수 응답과 양수 KRX 번호를 이미 보존한 신규 원주문이어야 한다. 번호 없는 불명 요청이나 정정·취소 주문은 대상이 아니다.
- 현재 계좌와 당일 거래일, 유일한 같은 주문번호, 종목·매수/매도 방향·현금 상품·신용 구분·원주문 수량·지정가가 일치해야 한다.
- 누적 체결수량은 주문 전량과 같고 미체결·확인수량·자동취소·기존 취소수량은0이어야 한다. 평균체결가는 양수이며 매수 지정가 이하·매도 지정가 이상이어야 한다. 이미 저장한 개별 체결의 수량·금액과도 일치해야 한다.
- 계좌에 연결된 조회는 해당 주문이 불명이 된 이후와 최근 계좌 변동 이후에 시작돼야 한다. 수신 후5초 이내에 적용하며 미래·오래된 시각, 잘못된 요청 범위, 중복 행·식별 충돌은 거부한다.

부분체결·미체결 잔여·다른 주문·체결금액 불일치나 확인되지 않은 상태를 전량체결로 만들지 않는다. 기존 정상코드`0`과 확인구분 공란의 독립 전량체결 경로는 각각의 근거로 구분한다.

## 저장과 이후 주문 검증

조건이 맞으면 별도의 `ModernAcceptedStateWithFullFill` 누적 체결 체크포인트를 저장한다. 원래 확인구분`1`, 설치 정의 프로필·SHA256·직렬화 형식,`접수` 상태, 거부정보 형태와 경로 근거를 함께 보존한다. 가짜 개별 체결번호를 만들거나 기존 체결에 누적 수량을 다시 더하지 않는다. 저널 재개방에서도 체크포인트의 계좌·식별자·수량·금액·근거를 재검사한다.

이후 새 주문의 Readiness는 **동일한 설치 정의 해시와 새 계좌 범위 조회의 같은 주문 행**을 다시 요구한다. 수량·평균가·확인 상태·거부정보·KRX 경로가 현재도 맞아야 하며 정의 변경이나 모순된 후속 증거는 주문을 막는다. 완료 체크포인트만으로 오래된 잔고·예수금·주문가능수량을 재사용하지 않는다.

후속 행이 같은 검증된 프로필·해시의 명시적인 정상코드`0`으로 바뀌더라도 나머지 대조 조건을 모두 다시 요구한다. 이 경우에도 저장된 체크포인트의 원본`1`과 접수 대조 출처는 고쳐 쓰지 않는다. 해시만 바뀐 행이나 프로필 미확인`0`은 이 체크포인트를 확인하는 근거가 아니다.

2.2.11은 기존 정상코드·공란 체크포인트를 읽는다. 새 근거 열거값을 저장한 저널은 이를 모르는 구버전 EXE에서 읽지 못하므로, 하위 버전과의 양방향 저널 호환성을 제공한다고 표시하지 않는다. 구조 검사는 저널 파일의 암호학적 위변조 방지를 의미하지 않으며, 후속 조회의 해시·계좌·수량 대조는 별도로 계속한다.

CSV는 기존 확인구분·거부정보·상태명에 정의 프로필·SHA256·주문방식코드·SOR 식별자 형태를 추가한다. 원본 공급자 메시지와 계좌 자격정보를 추가 열에 복사하지 않는다. 이 분류는 진단과 복구 근거를 구별하기 위한 것이며 개별 체결번호나 조회 전체의 완결성을 보장하지 않는다.

## 사용 순서와 실제 검증 범위

1. 성공한2.2.11 Windows 빌드의 EXE를 실행하고 Indi를 연결한다.
2. 계좌를 입력해 `실계좌 조회·감시`를 누른다. 현재 설치 정의와 최신 계좌·주문 조회를 대조한다.
3. 조건이 모두 맞아 `기존 주문 전량체결 대사 완료`가 표시되면 `실주문 운영 시작`을 누른다. 불일치가 있으면 표시된 대사 사유를 확인한다.

과거 주문은 자동 재전송하지 않으며 사용자가 거절 행을 골라 재시도할 필요도 없다. 대사가 완료돼도 실주문 승인을 자동으로 복원하지 않는다. 새 운영 시작 후 주문은 현재 전략·실시간 시세·현물 잔고·가능수량·주문가능금액·중복 검사를 다시 통과해야 한다. 대기 중 자동 종목 분석과 별도 매도판정 표시는2.2.10의 동작을 유지한다.

정적 정의 분석과 합성 파서·요청/콜백·저널·재시작·후속 Readiness·CSV·실제 폼 검사는 실제 사용자 서버 실행과 구분한다. 최종 수와 Windows 빌드 결과는 [TEST_REPORT.txt](../TEST_REPORT.txt) 및 [PR #1](https://github.com/na999jason-sketch/shinhan-autotrader/pull/1)에 기록한다. 이 작업의 도구로 실제 계좌 조회나 주문을 실행하지 않았다.

사용자 Windows에서 새 경로의 전량체결 대사와 이후 주문이 정상 완료됐는지는 아직 확인되지 않았다. 최초 AA·AD 실시간 오류의 근본 원인, 실제 매수·정정·취소·부분체결·재시작 복구와 무인운영의 전체 검증도 남아 있다. 이번 현행 프로필 대응을 확인구분 전체의 공식 의미 인증이나 수익성 검증으로 보고하지 않는다.
