# 접수 주문의 전량체결 복구 — 2026-11-13 KST

사용자2.2.7 진단에서 확인된 운영 중단과2.2.8 복구 범위를 기록한다. 계좌·주문 식별자, 사용자 경로, 원본 로그와 공급자 자료는 복사하지 않는다. 이 작업의 도구로 실제 계좌 조회나 주문을 실행하지 않았다.

## 실제 관측과 원인 구분

13:07~13:09 종목·잔고·현금·당일 주문 조회는 정상 수신됐다. 기존에 정상 접수된 매도가 재시작 후 `Unknown`으로 남아 주문 준비를 막았고,13:08:26과13:09:19에는 전체 중단 처리가 조회용 자격정보까지 해제했다. 정상 주문 조회를 기존 접수 주문의 복구에 연결하지 못한 프로그램 문제이며, 이 기록을 새 COM 연결 실패로 해석하지 않는다.

이전 실제 매도 접수 확인은 [접수와 실시간 장애 기록](ORDER_ACCEPTANCE_AND_RT_FAILURE_20261113.md)에 남아 있다. 최초 AA·AD 실시간 오류의 원인과 실제 개별 체결은 아직 확정되지 않았다. 잔고 행수 감소나 주문 조회 한 건만으로 체결 완료를 판단하지 않는다.

## 2.2.8 복구 조건

`실계좌 조회·감시`의 당일 주문 응답을 운영 시작 전에 대사한다. 자동 복구 대상은 양수 KRX 주문번호와 정상 접수 응답이 이미 보존된 신규 원주문이며, 다음 근거가 모두 필요하다.

- `SABA231Q1`의9개 요청 필드가 정해진 계좌·거래일 조회 범위와 일치하고, 모든 입력 설정 성공·양수 요청번호·일치하는 정상 콜백이 확인돼야 한다. 요청·수신 시각은 수신 과정에서 확정하며, 현재 계좌와의 연결은 임의 난수를 사용하는 비공개 메모리 지문으로 확인한다.
- 같은 계좌 지문·당일 거래일·보존된 KRX 주문번호에 대응하는 유일한 행이어야 한다. 종목·매수/매도 구분·상품`01`·신용`00`·원주문 수량·지정가가 같고, 거절·정정·취소나 다른 주문과의 식별 충돌이 없어야 한다.
- 체결수량이 원주문 전량과 같고 미체결·확인수량·자동취소수량은0이어야 한다. 평균체결가는 양수이고 지정가 범위에 맞아야 하며, 이미 보존된 개별 체결의 수량·금액과도 양립해야 한다.
- 조회는 해당 주문이 불명이 된 이후와 최근 계좌 변동 이후에 시작돼야 하며 수신 후5초 안에 적용해야 한다. 시각·계좌 연결 정보가 변조됐거나 오래된 자료는 사용할 수 없다.

번호 없는 불명 주문·부분체결·행 누락·중복·불일치는 계속 `Unknown`으로 남긴다. 빈 조회를 주문 부재의 증거로 사용하거나 과거 주문을 자동 재전송하지 않는다.

검증된 전량체결은 **증권사 누적 체결 체크포인트**로 저장하고 `증권사 전량체결 대사 완료`로 표시한다. 이를 개별 체결 목록에 넣거나 가짜 체결번호를 만들지 않는다. 먼저 받은 개별 체결은 체크포인트에 포함된 부분집합으로 대조하고 다시 더하지 않는다. 이후 AA 등에서 모순되는 증권사 증거를 받으면 완료 주문도 다시 `Unknown`으로 전환해 대사를 요구한다.

## 운영과 검증 범위

불명 주문이나 실시간 오류는 추가 주문 승인을 해제하되, 세션 메모리의 조회 자격정보·주문 기록·감시·보고서를 유지한다. 전체 중단을 반복해 복구 조회를 막지 않는다. 사용자의 `운영 중단`·앱 종료는 여전히 계좌 세션을 해제하며, 어느 경우든 이미 접수된 증권사 주문을 자동 취소하지 않는다.

복구 완료 후에도 **사용자가 `실주문 운영 시작`을 다시 눌러야 한다.** 새 주문의 계좌·잔고·주문가능금액·매도가능수량·미체결·시세·중복 주문 검증은 유지한다. 복구가 실시간 채널의 정상 동작이나 새 주문 조건을 대신하지 않는다.

코드의 합성 복구 검사는 통과했으며 최신 빌드·검사 결과는 [검증 기록](../TEST_REPORT.txt)과 [PR #1](https://github.com/na999jason-sketch/shinhan-autotrader/pull/1)에서 확인한다. **실제 Windows Indi 서버에서 이 복구 경로가 완료됐다는 증거는 아직 없다.** 실제 매수·정정·취소·부분체결·실시간 오류의 근본 원인·재시작 복구와 무인운영 검증도 남아 있다.
