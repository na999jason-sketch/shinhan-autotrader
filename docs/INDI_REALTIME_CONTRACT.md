# Indi 현물 실시간 시세·계좌 이벤트 대조

확인일: 2026-11-12. 공식 배포 설치 파일을 실행하지 않고 추출한 OCX와 Helper 조회 설명, 같은 IID의 공개 생성 Interop 메타데이터를 대조했다. 실제 서버 등록·실시간 수신·주문을 실행한 검증은 아니다. 사용자 PC의 설치 파일 해시가 아래 파일과 같다는 확인도 아직 없다.

## COM 실시간 등록과 이벤트 형식

명령 인터페이스 IID는 `B4A0D92F-6683-4824-9C63-53F7DAD7F57C`, outgoing 이벤트 IID는 `F52E833F-1D17-4184-BE0D-6B9F59DE7DAC`다.

| 멤버 | DISPID | 생성 Interop와 대조한 형식 |
| --- | ---: | --- |
| `RequestRTReg` | 6 | `bool(object type, object code)`, 두 입력은 `[MarshalAs(UnmanagedType.Struct)]` VARIANT |
| `UnRequestRTReg` | 7 | 위와 같은 두 VARIANT 입력, bool 반환 |
| `GetSingleData` | 8 | `object(short index)`, 반환은 VARIANT |
| `UnRequestRTRegAll` | 18 | 입력 없음, bool 반환 |
| `ReceiveRTData` | 2 | `void(object rttype)`, 입력은 `[MarshalAs(UnmanagedType.Struct)]` VARIANT |

**ReceiveRTData의 선언 인자는 VT_VARIANT다.** 그 안에 BSTR 문자열이 들어오는 것과 이벤트 선언 자체가 VT_BSTR인 것은 구분해야 한다. 공개 생성 Interop의 `object`/`MarshalAs(27)`과 공식 OCX의 실제 이벤트 호출이 이 점에서 일치한다.

공식 OCX의 RT 처리 경로에서 VA `0x10001F70`은 임시 VARIANT의 `vt=8`을 설정한다. `0x10001FAB`부터 해당 VARIANT 주소, VTS 서명 주소 `0x1000A23C`, DISPID2를 전달해 `0x10001FB7`에서 이벤트를 발생시킨다. `0x1000A23C`의 실제 바이트는 `0C 00 00 00`, 즉 VTS_VARIANT다. 내부 BSTR는 이벤트 호출 후 `0x10001FC3`에서 해제한다.

따라서 이벤트 인자와 GetSingleData 응답은 이벤트 콜백 안에서 복사해야 한다. 나중에 UI 큐에서 getter를 실행하면 원래 응답 버퍼를 보존하지 못한다. 같은 STA에서 이벤트 delegate를 보관하고 정확한 인스턴스로 해제하며, 조회·실시간·주문 OCX의 응답 버퍼를 섞지 않아야 한다.

등록 함수의 bool 반환은 등록 호출 결과다. 그것만으로 이후 시세의 신선도, 계좌 이벤트 전달, 재연결 중 누락 없음이 확인됐다고 표시하지 않는다. AA의 Helper 구역에는 등록키 설명이 없고, AD는 계좌번호와 전체키 `*`를 설명한다. 특정 계좌 등록키가 현재 서버에서 어떻게 적용되는지는 실제 수신 계좌와 대조해야 한다. 콜백의 계좌·상품을 먼저 검사하고 다른 계좌의 필드를 로그나 보고서에 복사하지 않는다.

처리구분0은 `00` 정상주문, `03` 체결, `04` 정정확인, `05` 취소확인, `09` 주문거부, `19` 접수거부, `98` 취소거부, `99` 반대거부를 설명한다. **누적 체결수량16을 새 개별 체결로 더하지 않는다.** 개별 체결은22·23·24를 조합해 실제 주문과 대조하고, 계좌·거래일·주문번호 범위 안에서 체결번호를 중복 제거한다.

정정·취소에는 원주문과 요청 주문의 결과가 별도로 도착할 수 있으므로32를 검사해야 한다. `00` 정상주문이나 상태01 접수를 체결·정정확정·취소확정으로 처리하지 않는다. 확인수량19와 실제 원주문/정정·취소 요청 수량이 일치하는지 검증하고, 불명확한 이벤트로 예약금·매도수량을 해제하지 않는다. Helper는29 일련번호의 전역 유일성이나 날짜를 보장하지 않는다.

## SABA609Q1과 매도 가능수량의 의미

입력은0 계좌번호,1 상품구분 `01`,2 비밀번호,3 기준구분 `1` 매매기준,4 단가구분 `1` 평균단가,5 종목구분 `0` 전체,6 작업구분 `0` 전체 출력이다. 단일0은 기준일자,3·6은 D+1/D+2 일자다.

반복 출력0 종목코드,2 기준구분,3 보통/융자 등 구분,4 잔고수량,9 결제일수량,10 **주문가능수량**,11 미체결수량,12 평균단가,13 현재가다. Helper는10을 명시적으로 `매도가능수량`이라고 부르지 않는다. 같은 계좌·상품·종목에 대해 AD8과 일치하는지 확인하는 것은 유용한 일관성 검사지만 그 자체로 현재 서버의 필드 의미를 독립적으로 검증한 결과는 아니다. 결제일 잔고수량에서 미체결을 임의로 빼 매도가능수량을 만들지 않는다.

## 주문 집계와 체결 복구 조회

SABA231Q1 입력5는 `0` 주문별 합산, `1` 체결건별이다. 반복 출력23은 **입력자**이며 체결번호가 아니다. 이 조회의 Helper/추출 XTR에는 고유 체결번호 필드나 명시적인 연속조회 키·마지막 페이지 출력이 확인되지 않았다. 건별 조회라는 이유만으로 시간·수량·가격을 합쳐 체결번호를 만들어서는 안 된다.

별도 공식 `TR_5200`은 현물 실시간 주문체결 조회이며 체결번호를 제공하는 복구 후보이다.

| 단일 입력 | 값 |
| ---: | --- |
| 0 | 계좌수: 단일 계좌는 `1` |
| 1 | 체결미체결: `0` 전체, `1` 미체결, `2` 체결 |
| 2 | 종목코드: 전체는 SPACE |
| 3 | 합산구분: `1` 주문별, `2` 종목별 |
| 4 | 매매구분: `0` 전체, `1` 매도, `2` 매수 |
| 5 | ECN: 현재 사용 안 함 |
| 6 | 계좌번호 리스트 |

반복0~29는 AA의 같은 번호 필드와 대부분 일치하며2 계좌번호,5 주문번호,6 원주문번호,11 종목코드,16 누적체결,20 미체결,22 체결번호,23 개별체결수량,24 체결단가,25 체결시간을 제공한다.30 체결금액,31 현재가,32 주문조건,33 체결금액 합계도 있다.

TR_5200의 합산 모드가 모든 개별 체결을 반환하는지 또는 주문별 마지막 체결만 반환하는지는 실제 서버에서 확인해야 한다. 반환된 고유 개별 체결의 수량 합과 알려진 주문의 누적 체결·미체결을 대조하고, 누락된 식별자나 수량이 있으면 대사를 완료 처리하지 않는다. 이 조회도 문서만으로 데이터 완결성을 보장하지 않는다.

공식 OCX의 TR 수신 코드에는 헤더 byte32가 `Y`일 때 플래그를 기록하고(`0x10001C3D`), T형 응답의 이벤트 발생을 건너뛰는 분기(`0x10001D00`~`0x10001D05`)가 있다. 이 플래그의 최종 패킷 처리와 조회 파싱은 별도 확인이 필요하다. 이 정적 분기만으로 서버의 검색 건수 제한이나 조회 완결성이 입증됐다고 표시하지 않는다.
